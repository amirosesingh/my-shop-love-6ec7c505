## 1. Executive summary

This is a multi-branch retail POS built as a TanStack Start React application
that ships in three shapes from one codebase: a browser app, a Windows Electron
till with its own Microsoft SQL Server database, and an Android Capacitor client.
The central system of record is a Lovable Cloud Postgres database.

**What the system does today (all CONFIRMED):** sells, holds and exchanges
baskets; splits tenders across payment types; opens and closes shifts with X/Z
reporting; manages products, categories, units, barcodes and SKUs; moves stock
between branches; receives purchase orders; runs a central membership programme
with coupons and vouchers; takes pay-later bookings and racket-service job
cards; prints ESC/POS receipts and kicks a cash drawer; drives a second-screen
customer display; and writes a human-readable audit trail plus branch telemetry.

**Architectural spine.** Everything of consequence funnels through four modules:

```text
UI/component  ->  src/lib/db-router.ts   (the only sanctioned data gateway)
                    -> src/lib/pos-db.ts     (commitOps: durable commit)
                       -> src/lib/sync-engine.ts (relay / outbox drain / pull)
                          -> src/lib/pos-relay.server.ts  (server-side write relay)
                             -> Postgres (RLS + SECURITY DEFINER routines)
```

Reads mirror it through `src/lib/db-query.ts`.

**Health of the system at audit time:**

- Database security posture is materially better than earlier audits reported.
  `anon` now has **zero** table grants (query returned an empty set), and **no**
  `SECURITY DEFINER` function is missing a pinned `search_path`. Both were
  previously flagged and are now CONFIRMED clean.
- 133 policies across 54 tables; 54/54 tables have RLS enabled.
- Two tables (`cashiers`, `pin_attempts`) have RLS on with **zero policies** —
  deliberately unreachable by the Data API and used only through
  `SECURITY DEFINER` routines. CONFIRMED, and correct by design.
- Eleven policies still evaluate to `true`; most are intentionally public or
  staff-wide reads, but three on `member_verifications` are broader than the
  data warrants (see [§18](#18-row-level-security-audit)) — RISK.
- Ten database routines are ORPHANED (legacy cashier / terminal-user CRUD,
  superseded by the `staff_account_*` and `app_users` family).
- The commit path is idempotent and durable; the weakest link is the number of
  swallowed `catch {}` blocks in peripheral modules ([§38](#38-error-handling-audit)).

## 6. The write path

**Rule: nothing writes to the network directly. Everything goes through
`dbRouter.write` → `commitOps`.** (`src/lib/db-router.ts`, `src/lib/pos-db.ts`)

`commitOps(context, ops)` resolves only once the data is durable, and returns
where it landed: `"cloud" | "local" | "outbox"`. Callers `await` it before
printing, clearing the cart or starting the next action.

Sequence inside `commitOps` (CONFIRMED, `pos-db.ts:1327`):

1. `hydrateTerminalConfig()` — a packaged till may carry an encrypted tenant
   override; this stops an early write resolving against the build-time tenant.
2. `withRelativeStock(ops)` — if the batch contains `item_activity_logs` rows,
   the `products` upsert is **stripped of `stock_quantity` / `stock_by_store`**
   and the movements become relative deltas keyed on the movement id. This is
   why a replay can never deduct stock twice.
3. Platform fork:
   - **Live-only (Android):** every op goes through `runOpLive`; connection-class
     failures throw `AllTargetsFailed`.
   - **Desktop with local SQL:** cloud first. On success, `mirrorToLocal` copies
     rows to the local engine in the background (failures only reach the sync
     log — the operator is never interrupted after a completed sale). On a
     *connection-class* failure only, it falls back to the local engine and
     returns `"local"`. Validation and permission errors are re-thrown and stay
     visible — CONFIRMED, and an important design decision.
   - **Browser:** cloud or fail. Operational business data is never parked in
     browser storage.
4. `applyStockDeltas` calls the batched `stock_apply_deltas` RPC — one round trip
   per basket. Refusals are logged and parked, never thrown, because the movement
   rows are already stored and can be reconciled.

`useCommit()` (`src/lib/use-commit.ts`) is the UI wrapper: a `busy` ref makes a
second submit impossible while the first is saving, success toasts state where
the data landed, failures leave the screen untouched.

**Idempotency:** sales carry `client_transaction_id`; stock deltas are keyed on
`movementId`; inserts use the row id as the conflict key, so replays upsert
rather than duplicate. CONFIRMED (`checkout-e2e.test.ts`, `stock-delta-batch.test.ts`).

## 7. The read path and query routing

`dbRouter.query(table, options)` / `queryWithSource` delegate to
`src/lib/db-query.ts`, which:

- picks central-first when the device is set to work online and the line is up,
  otherwise the terminal's own copy;
- deduplicates identical in-flight queries;
- reports the source so a screen can tell the operator what they are looking at.

`dbRouter.read(live, local)` is the manual variant: it falls back to a cached
value **only** when `isConnectionError(e)` — a permission or validation error is
never masked by stale data. CONFIRMED (`db-router.test.ts`).

Column-tolerant reads: `pos-db.ts` keeps sets of columns an older database may
not have (checkout-attempt columns, branch-name snapshot columns, unknown
`pos_settings` columns). The first "column not in schema cache" refusal
permanently downgrades later queries instead of failing the screen. This keeps
old deployments alive but silently hides genuine schema drift — PARTIAL/RISK.

## 8. Offline queue, sync engine and conflict handling

**The queue** (`src/lib/sync-outbox.ts`): entries carry `branchId`, `terminalId`,
a monotonic per-terminal `seq`, `occurredAt`, attempt count and `baseVersions`
(the record version the till was working from, from `src/lib/row-versions.ts`).

- `canQueue()` = has local engine **and** not live-only. A plain browser build
  never queues business data.
- Backoff: `1s, 2s, 4s … capped at 30s`, plus a deterministic jitter derived from
  the entry id so the countdown shown on screen matches the engine's.
- `MAX_ATTEMPTS = 10`, after which the entry is **quarantined** (dead letter).
- `refuseOp` parks immediately for principled refusals (wrong branch, missing
  permission) — retrying cannot help.
- `discardOp` / `discardQuarantined` call `localRollback` over IPC so the till
  stops showing a change that will never be sent.
- `persisted(ids)` re-reads from disk: the commit layer only continues once the
  data is genuinely on storage.

**The engine** (`src/lib/sync-engine.ts`):
`runOpLive` (immediate send), `drainOutbox` (replay in happened order),
`pullDelta` (bring down central changes since the last clean pull, per-table
timestamp column probed once and cached), `pushLocalPending` then pull = the two
convergence phases. Catalogue pulls are **server-wins** and overwrite locally.
Refusal codes from the relay are recognised and parked; unknown-column errors
strip the column and retry; a session that has been refused a table once stops
retrying that table for the session.

**Conflicts:** last-write-wins with version guards. The change carries the base
version; the central copy's resulting version is checked afterwards, and a
divergence is recorded in `pos.sync.conflicts` and surfaced on Sync & backup.
`src/utils/syncResolver.ts` and `src/lib/sync-conflicts.ts` hold the merge rules.

## 9. The server write relay

`src/routes/api/public/sync.ts` + `src/lib/pos-relay.server.ts` +
`src/lib/relay-policy.server.ts`. This is a service-role endpoint, so its
authorisation logic *is* the security boundary. CONFIRMED reading
`relay-policy.server.ts`:

1. `resolveRelayScope(caller)` derives branch, identity and permissions from the
   verified token claims, re-reading `app_users` when claims are incomplete. If
   the identity is known but permissions are not, writes are refused as stale.
2. `RELAY_WRITABLE_TABLES` is an allow-list. Anything else → `TABLE_FORBIDDEN`.
3. Branch scoping: every op must match the caller's branch unless the caller is a
   supervisor (admin/manager). Missing scope → `SCOPE_MISSING`
   ("This till is not assigned to a branch — sign in again.").
4. `TABLE_PERMISSIONS` gates write and remove per table; a column→permission map
   re-checks sensitive columns (e.g. price fields) → `PERMISSION_DENIED`.
5. `GLOBAL_TABLES` (`products`, `members`, `audit_logs`) skip branch scoping but
   keep column gating; `stock_transfers` and `stores` have bespoke rules.

Denial codes: `TABLE_FORBIDDEN`, `SCOPE_MISSING`, `PERMISSION_DENIED`, and
branch-mismatch. All are terminal — the outbox parks them rather than retrying.
Covered by `relay-policy.security.test.ts`.

## 11. SQL Server connection and authentication handshake

This was historically the most failure-prone area; the current design is a
budgeted attempt ladder with a cancellable state machine. CONFIRMED from
`electron/db/pool.cjs` and `electron/db/admin-pool.cjs`.

**Budgets** (`pool.cjs`):

| Constant | Value | Meaning |
| --- | --- | --- |
| `CONNECT_TIMEOUT_MS` | 15 000 | driver-level connect timeout |
| `LADDER_BUDGET_MS` | 25 000 | hard ceiling for the whole ladder — the UI always gets an answer |
| `ATTEMPT_TIMEOUT_MS` | 8 000 | no single attempt may eat the budget |
| `SOCKET_TIMEOUT_MS` (admin) | 2 000 | raw port probe |
| `CONNECT_TIMEOUT_MS` (admin) | 15 000 | admin pool open |

**Ladder** (`securityLadder` + `planAttempts`): the requested security setting
first, then `{encrypt: true, trust: true}`, then `{encrypt: false, trust: true}`,
across the available drivers (`tedious` and, for Windows Integrated
Authentication, `msnodesqlv8` with the installed ODBC drivers enumerated by
`installedOdbcDrivers()`). A driver that fails with a driver-class error is added
to `deadDrivers` and skipped; once one driver works, the others are skipped.
Named instances resolve through `parseServerField` / `resolveTarget`, falling back
to a fixed TCP port when the SQL Browser service is unavailable.

**Error vocabulary** (`describeSqlError`, plain-language by design):
`ELOGIN`, `ETIMEOUT` ("firewall, wrong port, or a stopped SQL Server Browser"),
`ETIMEOUT_INSTANCE_LOOKUP`, `EDRIVER`, and `EBUDGET` — the last explicitly tells
the operator the deadline ended while walking combinations, *not* that a port
probe failed. Every attempted combination is returned to the UI.

**State machine** (`admin-pool.cjs`): each run gets an `attemptId`; a new
`connectInstance` **supersedes** the running one (`await cancel()`) rather than
refusing with "busy" — this is the fix for the Windows Integrated Auth lock.
`withDeadline` guarantees a client-side answer, `run.cancelled` short-circuits
every stage, and a pool that opens after cancellation is closed immediately so no
handle leaks. `trace()` logs `attempt / stage / event / elapsed` for every step.
`lockDatabase` performs a real write round-trip (`verifyWrite`) before declaring
success, which is what made "Lock & Save" stop hanging.

The read-only guard `validateReadOnly(text)` gates `sqladmin:query`, so the
explorer cannot mutate the operational database.

### 11.1 Isolated Windows Authentication driver (v1.3.24)

Windows Integrated Authentication uses `mssql/msnodesqlv8`, a native ODBC
binding. A stuck native `connect()` cannot be interrupted from JavaScript: a
Promise timeout only stops *waiting*, and closing or replacing the pool while
the native call is in flight used to take the whole Electron process down —
the "POS did not start correctly" screen. It therefore no longer runs in the
main process at all.

| File | Role |
| --- | --- |
| `electron/db/native-worker-entry.cjs` | the ONLY module that loads `mssql/msnodesqlv8`; holds no policy |
| `electron/db/native-client.cjs` | main-process supervisor: deadlines, kill-based cancellation, crash counter, worker pool, session accounting |
| `electron/db/native-protocol.cjs` | request/response wire format, value/type/error encoding |
| `electron/db/sql-target.cjs` | single source of truth for direct-mode targets and the migration audit |

Rules enforced by the design:

- **Isolation** — the main process never requires the native driver. SQL Server
  Authentication is untouched and stays on pure-JS `tedious` in the main process.
- **Attempt identity** — every message carries an `attemptId`; a reply for an
  attempt that already timed out or was reaped is logged as
  `driver.reply-discarded` and never reaches app state.
- **Cancellation** — the only cancellation primitive is `worker.kill()`.
  Nothing calls `.close()` on a connection whose native connect may be running.
- **Crash loop** — three consecutive `EDRIVER_CRASH` results on one target
  (`CRASH_LIMIT`) switch it to `EDRIVER_CRASH_LOOP`: automatic retrying stops
  and the settings panel shows a hard error. "Reconnect now" clears the block.
- **Worker pool** — a warm worker is reused; `MAX_WORKERS = 2` caps concurrent
  driver processes so a retry burst cannot flood the machine.
- **Session cleanup** — a kill skips TDS logout, so the SPID is recorded and
  closed through a side-channel `KILL_SESSION`; unresolved orphans past
  `ORPHAN_WARN_AT` raise a warning in Local database settings.
- **Direct-mode determinism** — `normalizeDirectTarget` turns `PCNAME\SQLEXPRESS`
  plus a pinned port into `PCNAME,port` once, and every path (admin handshake,
  lock flow, operational pool) uses that same string. SQL Browser is never
  consulted in direct mode.
- **Migration guard** — `auditConnectionConfig`, exposed as `pos:connection-audit`,
  flags any saved named instance with no pinned port (`EMISSINGPORT`) before it
  fails at the first sale.

The main process also installs `uncaughtException` / `unhandledRejection`
handlers that write to `connection.log` and keep the window alive, and the saved
connection is no longer awaited during boot — the register renders first.

### 11.2 Durable crash evidence (v1.3.24)

Previously a crash could leave nothing behind: native faults produced no
minidump, the local app server's output went to a console nobody sees, and a
dead renderer was only inferred one boot later. `electron/diagnostics.cjs` now
writes to the user data folder that the recovery screen already reveals:

| File | Written by |
| --- | --- |
| `crash.log` | uncaught exceptions, `render-process-gone`, `child-process-gone`, unresponsive windows, `did-fail-load`, app-server exits |
| `server.log` | every line of the local app server's stdout/stderr |
| `connection.log` | the SQL attempt ladder (existing) |
| `diagnostic-report.txt` | on demand — machine facts plus the tails of the three logs above |
| crash dumps | `crashReporter` minidumps, upload disabled — local folder only |

All logs rotate once at 512 KB and every write is wrapped: logging may never be
the reason the till stops. "Save diagnostic report" appears both in Local
database settings and on the recovery screen, so a shop can send one file
instead of describing a crash.

**Driver auto-install** (`electron/db/driver-install.cjs`, `driver-catalog.json`,
`src/components/database/DriverInstallPanel.tsx`). When the ladder ends in
`EDRIVER` the wizard offers a one-click install of the missing Microsoft driver.
The catalogue pins ODBC Driver 18 / 17 and OLE DB Driver 19 (x64 `.msi`) to their
official `download.microsoft.com` URLs with SHA-256 fingerprints. The flow is
download (streamed through the main process with percent progress) -> SHA-256
verification -> `msiexec /i <msi> /qn /norestart`, which raises Windows' own
elevation prompt; the temp file is always deleted. Exit codes map to `OK`,
`OK_RESTART` (3010/1641), `ECANCELLED` (1602/1223) and `EEXIT`. A mismatched
checksum deletes the file and never installs. On success the installed-driver
list is re-read and the handshake step re-runs with no app restart. Every phase
is logged to `connection.log` via `logConnection`. IPC: `driver:list`,
`driver:install`, `driver:progress`.

## 22. Sale and checkout flow

The Register (`src/routes/index.tsx`) is decomposed into hooks in
`src/lib/register/`:

| Hook | Responsibility |
| --- | --- |
| `use-cart.ts` | lines, quantities, line discounts, totals |
| `use-promotions.ts` | applies `promotions` rules to the basket |
| `use-tender.ts` | split tenders, change due, rounding |
| `use-checkout.ts` | the commit orchestration |
| `use-exchange.ts` | exchange / return basket mode |
| `use-held-orders.ts` | park and resume baskets (`held_orders`) |
| `use-booking-intake.ts` | pay-later bookings from the register |

End-to-end sequence (CONFIRMED, `checkout-e2e.test.ts`):

```text
scan/lookup -> cart line          (product-lookup.ts, product_barcodes)
member attach                     (members, membership_tiers)
promotions applied                (pos-promotions.ts)
tax computed                      (settings tax matrix; tax-matrix.test.ts)
tender(s) taken                   (use-tender.ts; payment_types)
shift must be open                (shift_active_for_branch — hard gate)
bill number allocated             (bill-number.ts; pos.bill.seq + terminal no)
commitOps([...sales, sale_items, payment_transactions, item_activity_logs])
   -> durable: cloud | local | outbox
ONLY THEN: print receipt, kick drawer, update customer display, clear cart
```

The "only then" ordering is deliberate and enforced in `use-checkout.ts`:
hardware side effects are gated behind a successful commit so a printed receipt
can never exist for an unsaved sale.

Bill numbering: `src/lib/bill-number.ts` combines a per-terminal number
(`pos.bill.terminalNo`) with a persisted sequence (`pos.bill.seq`), so two tills
offline at the same time cannot collide.

## 25. Shifts — open, close, X/Z reports

## 26. Inventory and stock movement

**The rule: stock never travels centrally as an absolute number.**
Movement rows (`item_activity_logs`) go up, and the database applies each one as
a relative change keyed on the movement id (`stock_delta_applied` records which
movements have landed). A retry therefore cannot deduct twice.

- Batch application: `stock_apply_deltas` — one round trip per basket
  (previously N). `stock_apply_delta` remains for single movements.
- Failure handling: refusals are logged and parked, not thrown; the sale is
  already complete.
- `src/lib/stock-recovery.ts` retries parked deltas with exponential backoff and
  keeps the unapplied set in `pos.stock.unapplied`.
- `stock_reconcile` detects drift between the movement ledger and the product
  stock figure; surfaced in the inventory hub.
- `stock_adjustments` covers manual corrections (permission-gated, audited).

## 37. Security audit

**Strong points (CONFIRMED):**

1. `anon` holds zero table grants; public functionality runs through
   `SECURITY DEFINER` routines and `/api/public/*` handlers.
2. Every `SECURITY DEFINER` function pins `search_path`.
3. Roles live in a separate `user_roles` table read through `has_role()` — no
   role column on a profile table, so no privilege-escalation-by-profile-update.
4. Permission enforcement is duplicated at three layers: UI gating,
   relay authorisation (`relay-policy.server.ts`), and database triggers
   (`enforce_*_permissions`). A compromised client cannot escalate.
5. PIN verification and throttling are entirely server-side against a
   policy-free table.
6. The SQL explorer is read-only enforced (`validateReadOnly`).
7. Secrets are server-only and never reach the bundle.
8. Views use `security_invoker=true`, so they do not become an RLS bypass.

**Findings:**

| # | Severity | Finding |
| --- | --- | --- |
| # | Severity | Finding | Status |
| --- | --- | --- | --- |
| S1 | Medium | `member_verifications` had three `true` policies for all `authenticated` users. | **Fixed v1.3.25** — read/insert/update now require `is_staff_now()` and `store_visible(store_id)`. |
| S2 | Low | `product_barcodes_write` allowed any authenticated user to write barcodes. | **Fixed v1.3.25** — writes require `is_staff_now()`; reads unchanged. |
| S3 | Low | `/api/public/*` endpoints self-verified per handler with no shared guard. | **Fixed v1.3.25** — `src/lib/public-api-guard.server.ts` holds the caller checks (`verifyHmacSignature`, `verifySharedSecret`, `publiclyReadable`); `security-alerts.ts` uses it. |
| S4 | Low | Orphaned legacy routines remained callable. | **Fixed v1.3.25** — EXECUTE revoked from `anon`/`authenticated` on `upsert_terminal_user`, `delete_terminal_user`, `set_terminal_active`, `set_app_user_profile`, `staff_account_set_pin`, `user_cluster_id` (kept, not dropped, so an older till build cannot hard-fail). |
| S5 | Informational | Column-tolerance fallbacks in `pos-db.ts` downgraded queries silently. | **Fixed v1.3.25** — each dropped column is announced once via `console.warn`. |

No hardcoded credentials, no client-side admin checks, and no
`localStorage`-based privilege decisions were found.

## 38. Error handling audit

- The commit path distinguishes **connection-class** failures (fallback allowed)
  from validation/permission failures (must surface) via `isConnectionError`
  in `src/lib/db-mode.ts`. This distinction is the backbone of correctness — a
  permission error must never be quietly written to a local database and
  "succeed".
- `AllTargetsFailed` produces the modal that tells the operator the data could
  not be stored anywhere. Nothing continues past it.
- `src/lib/error-capture.ts`, `ErrorNotifier`, `lovable-error-reporting.ts` and
  the root `errorComponent` form the display layer; `pos.health.errors` keeps a
  local ring buffer.
- **RISK:** ~151 `catch` blocks across `src/` and `electron/` swallow the error
  with a comment only. In peripheral modules (theme, UI scale, accent, camera,
  recent banks) that is correct. In these it deserves a review because a silent
  failure changes business state: `src/lib/bill-number.ts` (3),
  `src/lib/web-bundle-updates.ts` (3), `src/lib/audit-log.ts` (2),
  `src/lib/mobile-storage.ts` (2), `src/lib/customer-display.ts` (2),
  `src/lib/merge-guard.ts`, `src/lib/held-orders.ts`, `src/lib/active-branch.ts`,
  `src/lib/branch-settings.ts`, `src/lib/whatsapp-queue.ts`,
  `src/lib/activity-events.ts`.
  `bill-number.ts` is the highest-value one: a swallowed storage failure there
  can hand out a duplicate bill number.

## 39. Performance notes

- `src/lib/db-query.ts` deduplicates concurrent identical reads and caches health
  for two seconds.
- `src/lib/pos-persist.ts` debounces global-state persistence, so a fast scan
  loop does not serialise the whole POS state per keystroke.
- Sale reads select an explicit column list — no `SELECT *` — so a growing schema
  does not inflate every read (`pos-db.ts:542`).
- History uses keyset paging on `(created_at, id)`; the register keeps the most
  recent 500 bills in memory and never pays for an `OFFSET`.
- `stock_apply_deltas` collapsed N stock round trips into one per basket.
- 182 indexes; a duplicate index on `sales(client_transaction_id)` was previously
  dropped.
- The Register is split into seven hooks, which keeps re-render scope narrow.

## 44. Troubleshooting playbook

**"Cannot connect to SQL Server" on the till**
1. Read the attempt list in the dialog — every combination tried is shown.
2. `EBUDGET` means the 25 s ladder ran out, not that the port is closed.
3. `ETIMEOUT_INSTANCE_LOOKUP` → start SQL Server Browser or enter the fixed port.
4. `EDRIVER` with Windows Integrated Auth → `msnodesqlv8` / ODBC driver missing.
5. Use **Reset connection** in the dialog; a new attempt supersedes a stuck one.

**"Authenticate handshake" appears stuck**
It cannot exceed 25 s. If the UI still looks stuck, the renderer lost the IPC
reply — check `[sqladmin] attempt=… stage=… event=…` lines in the Electron log.

**Sale saved but nothing printed** — the commit succeeded and the printer failed.
Check `print:list`, the printer share name, and reprint from `/receipts`.

**Sale will not save at all** — the "could not be stored anywhere" modal means
cloud and local both refused. Check the status pill: "Cloud direct" means local
is unavailable; no connection at all on a browser build blocks operational writes
by design.

**Queue not draining** — Sync & backup shows each entry's state, reason and next
attempt. "Refused" entries are terminal: read the reason (branch mismatch or
permission) and fix the cause, then Retry.

**Stock figures look wrong** — run stock reconciliation (`stock_reconcile`);
check `pos.stock.unapplied` for parked deltas.

**Till says "not assigned to a branch"** — the relay could not resolve a scope;
sign in again to refresh claims.

**Terminal shows the activation screen unexpectedly** — the token was revoked or
`pos.terminal.config` was cleared; re-pair from the admin terminals screen.

**Shift will not close** — held orders remain, or unsent operational writes are
queued.

## 45. Operations runbooks

### 45.1 Run locally

Prerequisites: Node 20 LTS+ (22 recommended for mobile builds), the `.env` file
with the backend URL and publishable key.

```bash
npm install
npm run dev        # http://localhost:8080
```

Harmless warnings: `npm WARN deprecated`, peer-dependency warnings, Vite
"Re-optimizing dependencies". On Windows PowerShell blocking `npm.ps1`, use
Command Prompt or `Set-ExecutionPolicy -Scope CurrentUser RemoteSigned`.

Desktop dev: `npm run desktop:dev`. Package: `npm run desktop:package`,
installer: `npm run desktop:installer`.

### 45.2 Windows till with local SQL Server

1. Install SQL Server Express, enable TCP/IP for the instance.
2. Create an empty database (default `LovablePOS`) — tables are created on first
   connect from `electron/db/*.sql`.
3. `npm install`; for Windows Integrated Authentication also
   `npm install msnodesqlv8` (needs VS Build Tools).
4. Pair the terminal, then use **Lock & Save** — it performs a real write
   round-trip before declaring success.

### 45.3 Android APK

The phone app is a **live client**: no business data on the device, every read
and write hits the backend, and `OfflineGate` shows a "no connection" screen
otherwise. Build on GitHub via the **Android APK** workflow (leave the app-URL
box blank for the real app) or locally with Node 22, Bun, JDK 21 and the Android
SDK (`npm run mobile:build`, `npm run mobile:sync`). Updates install through a
FileProvider intent; the feed lives on the R2 domain.

### 45.4 Cloudflare hosting and release pipeline

```text
pos.<domain>          -> Worker (app)            [access-gated]
member.<domain>       -> Worker, /join           [public]
redeem.<domain>       -> Worker, /claim, /c/...  [public]
updatecms.<domain>    -> R2 bucket               [public reads]
```

One-time: Cloudflare API token (Workers Scripts Edit, R2 Edit, Workers Routes
Edit), account id, R2 custom domain, cache rules (`*.exe|apk|zip|blockmap` →
1 month; `latest*.json`, `*.yml` → bypass so tills see new versions at once).
CI deploys `main`; `scripts/desktop-release.cjs` and `scripts/android-release.cjs`
upload artefacts. Hostname behaviour is decided by `src/lib/coupon-hosts.ts`.

### 45.5 Secrets

Nothing secret is committed. Publishable URL + anon key are public by design and
read from env with a built-in fallback. `SUPABASE_SERVICE_ROLE_KEY`,
`SETTINGS_ENCRYPTION_KEY`, `SECURITY_ALERT_INGEST_SECRET` and `WHATSAPP_TOKEN`
belong in the hosting secret store and are read inside handlers only.

### 45.6 Version bumps

`node scripts/bump-version.cjs` regenerates `src/version.ts`; never hand-edit it.
`npm run logic:scan` refreshes `src/lib/logic-health.report.json`.
