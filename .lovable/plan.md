# Secure Cloud Credentials + Strict Local-First Sync — Implementation Preview

## What exists today (confirmed by code reads)

- **Already OS-encrypted (safeStorage/DPAPI):** SQL Server connection (`electron/db-config-store.cjs`), bundled-server service key + signing key (`electron/server-keys.cjs` via `config-store.cjs`), terminal activation (`electron/terminal-store.cjs`).
- **Not encrypted / hardcoded:** the central Supabase URL + publishable key are hardcoded in `src/lib/external-supabase-config.ts` (`POS_PROJECT`, lines 19–22) and pushed renderer → main on every launch via `AppShell.tsx` `configureCloud` effect (lines 167–184). The sync worker (`electron/sync/worker.cjs`) holds credentials only in memory; there is no sealed cloud-credential store and no Settings UI to enter them.
- **Local-first is mostly in place:** Electron defaults to `"local"` mode (`db-mode.ts:46`), checkout runs over IPC (`window.electronAPI.createSale`), the worker pushes `is_synced = 0` rows every 30 s. Missing: a credential-failure pause state, a startup setup popup, and a settings module for cloud keys.
- **Naming note:** the real IPC bridge is `window.pos.*` (not `window.electron.saveDbConfig`). New handlers follow that convention.

## Hard constraint (needs your acceptance)

`src/integrations/supabase/client.ts` is **auto-generated by the platform and cannot be edited** — it is overwritten on regeneration. It only serves platform features. The POS data plane (login, sync, relay, catalog) runs entirely through `src/integrations/supabase/external-client.ts` + `src/lib/external-supabase-config.ts`, which is where dynamic, IPC-fed initialization will be implemented instead. Also: the **publishable (anon) key is public by design** — the browser/web build has no safeStorage, so a build-time publishable fallback must stay for web only; Electron will prefer the sealed per-machine values. The **secret/service key never ships to the renderer** — it stays in the main process.

## Files to CREATE (3)

1. **`electron/cloud-credentials.cjs`** — new sealed store for `{ supabaseUrl, apiKey }`, mirroring `db-config-store.cjs`: `read()` / `write()` / `remove()` / `status()` (returns presence + masked hint like `sb_p…7Cg`, never the value), sealed with `safeStorage` (DPAPI on Windows), owner-only file perms, plain-JSON fallback only when the OS vault is unavailable (same documented trade-off as `config-store.cjs`).
2. **`src/lib/cloud-credentials.ts`** — typed renderer wrapper over the new IPC: `cloudKeyStatus()`, `saveCloudCredentials(url, key)`, `testCloudCredentials(url, key)`, `removeCloudCredentials()`, `initCloudConfigFromShell()`.
3. **`src/components/pos/settings/panels/CloudConnectionPanel.tsx`** — "Database & Cloud Connection" settings module (Manager/Admin only, mounted beside `ServerKeysPanel`): Central Supabase Project URL + Secret/Terminal Key inputs (password field, never prefilled), **Test Connection** button (throwaway client → `GET /auth/v1/health` + a minimal REST probe, reports the exact failure), **Save** (IPC → safeStorage, then hot-restarts the sync worker), **Remove** (deletes the sealed file, pauses sync).

## Files to EDIT (7)

4. **`electron/preload.cjs`** — add 4 additive bridge methods on `window.pos`: `cloudKeyStatus`, `setCloudCredentials`, `testCloudCredentials`, `removeCloudCredentials`, plus `onCloudSetupRequired(cb)` event listener. No existing channel changed.
5. **`electron/main.cjs`** —
   - Register the 4 new IPC handlers.
   - New `bootCloudFromSealedStore()`: after `startAppServer()`, read sealed cloud creds and call existing `initializeWorker()` with them — sync no longer depends on the renderer pushing config first. Renderer-pushed config still works as fallback for machines with no sealed entry yet (and is then sealed on save).
   - On `ready-to-show`: if no sealed URL+key exist, send `cloud:setup-required` to the renderer (non-blocking).
   - Add the key to `serverKeys.serverEnv()` injection path only if absent (unchanged behavior otherwise).
6. **`electron/sync/worker.cjs`** —
   - New credential-guard: detect 400/401/`invalid apikey`/JWT errors in `cloudUpsert()` and `pull()` → set `credentialsInvalid = true`, park **all** cloud traffic silently (no retry storm), keep every local row queued (`is_synced = 0`), expose `credentialsInvalid` + masked target in `status()`. Any successful call clears it and resumes automatically.
   - `init()` accepts creds sourced from the sealed store; no signature change for existing callers.
7. **`src/lib/external-supabase-config.ts`** — add `applySealedCloudConfig(url, key)` which routes through the existing `setTerminalSupabaseOverride()` so the entire renderer (external client, sync engine, relay, login) switches tenant without restart. Electron bootstraps from the sealed store; the hardcoded `POS_PROJECT` publishable pair remains **web-only fallback** (Electron with sealed creds never touches it).
8. **`src/components/pos/AppShell.tsx`** — on launch (Electron only): call `initCloudConfigFromShell()` before the existing `configureCloud` effect; that effect is adjusted to skip pushing build-time creds when the shell reports sealed creds present. Listen for `onCloudSetupRequired` → show a dismissible dialog: "Cloud Sync Setup Required — configure your Online Database Keys in Settings" with **Open Settings** (`/settings/system`) and **Continue offline** buttons. Nothing is blocked: login, sales, and printing proceed.
9. **`src/components/pos/sync/SyncBadge.tsx`** (+ `src/lib/sync-status.ts` if a new tone needs plumbing) — two new states: **"Offline / Unconnected"** (no sealed keys) rendered as a badge with a "Connect to Online Database" link to Settings; **"Sync Paused — Check Credentials"** when the worker reports `credentialsInvalid`. Existing online/syncing/offline/error logic untouched.
10. **`src/routes/settings.system.tsx`** — mount `CloudConnectionPanel` above `ServerKeysPanel` in the "system" tab (one-line JSX addition).

## Explicitly NOT changed (zero-disruption guarantees)

- No changes to: cashier login (`CashierPinLogin`, `staff:verify-pin`), shift open/close, `pos-auth.tsx`, role/permission tables, RLS policies, checkout (`db:create-sale`), printing, the local schema manager, or any existing IPC handler signature.
- Auth user creation, role assignment, and offline PIN login against local SQL remain byte-for-byte the same — the refactor only changes **where cloud credentials live** and **when the sync worker runs**.
- Browser/Android builds behave exactly as today (build-time publishable config, no safeStorage path is reached).
- No new secrets are committed — `secrets.security.test.ts` continues to pass; the hardcoded pair being kept is a publishable key, which that test explicitly allows.
