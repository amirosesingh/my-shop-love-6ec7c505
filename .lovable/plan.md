# Runtime-configurable connectivity: one build, many customers

Scope is connectivity/configuration only. SQL Server, SQLite/offline, sync, RLS, server secrets and Emergency Access design are untouched.

## 1. No backend address baked into device builds

`src/lib/server-origin.ts`: drop the `VITE_POS_SERVER_URL` build fallback for terminal shells. `configured()` becomes runtime-only (`window.__POS_SERVER_URL__`, hydrated from the device store). Web keeps returning `""` (relative URLs). `serverUnreachableOnDevice()` then reports true on an unconfigured device, which routes it into the existing setup screen instead of a stale address. `vite.config.ts` / `scripts/web-only-env.cjs` lists updated so the name is no longer injected for device builds.

## 2. Environment file

Untrack `.env` (`git rm --cached` equivalent via tooling), confirm `.gitignore` covers it, and rewrite `.env.example` with names + placeholders only:

```text
SUPABASE_URL=                       # local web dev: your own project
SUPABASE_ANON_KEY=                  # publishable/anon key (public)
POS_SUPABASE_SERVICE_ROLE_KEY=      # server-only, worker/hosting secret
SETTINGS_ENCRYPTION_KEY=            # server-only
```

Cloudflare deployment is unaffected — it reads its own Variables & Secrets through `setRuntimeEnv`. Local dev now needs a developer-supplied `.env`, documented in the example file and README note.

## 3. Managed Supabase files quarantined

`src/integrations/supabase/{client,client.server,auth-middleware,auth-attacher}.ts` are Lovable-generated and read `VITE_SUPABASE_*`. They are already unregistered in `src/start.ts` and unimported by app code. They stay on disk (regenerated by the platform) but get a guard test asserting no file under `src/`, `electron/` or `scripts/` imports them — extending the existing `own-database.security.test.ts` guard rather than adding a new mechanism. Comment headers state the app's only config path is `external-supabase-config.ts`.

## 4. One connection profile

New shared type and single write path, implemented in `src/lib/secure-cloud-config.ts` with the backend half delegated to `src/lib/backend-config.ts`:

```ts
type ConnectionProfile = { supabaseUrl: string; supabaseKey: string; backendUrl: string };
saveConnectionProfile(input): Promise<{ ok, stage, detail, profile? }>
```

Order: normalise all three URLs → validate shapes → test cloud credentials → test backend address → only then write both stores (Electron OS vault + sealed config store; Android Keystore + device storage) → apply `setTerminalSupabaseOverride()` and `window.__POS_SERVER_URL__`. Any failure writes nothing, so no partial URL/key state. Terminal/branch identity keeps coming from activation and is read alongside the profile, not duplicated into it. No SQL Server credentials in the profile.

## 5. Readiness states

`src/lib/platform-config-ready.ts`: readiness now requires cloud pair **and** backend address. `state` becomes `not-applicable | missing | incomplete | testing | failed | ready`, each with a short reason, and `subscribeConfigReady` also fires on backend-address changes.

## 6. First run and reconfiguration

- `ConnectDatabaseScreen` (Android + Electron): shown whenever readiness is `missing`/`incomplete`/`failed`. Three fields, one **Test connection** (reports cloud reachability, key acceptance and backend answer separately), then **Save and continue** enabled only after a successful test, then straight to login. Reconfiguration never needs a reinstall.
- `CloudConnectionPanel` + `src/routes/settings.database.tsx`: post-install edits go behind the existing manager authorization gate (`@/lib/manager-gate`), same as other privileged settings. Flow: authorize → edit → test → save → reconnect. Read-only summary until authorized; cashiers cannot redirect the till.
- Emergency Access keeps its current role: a protected route back to this screen, never the credential store.

## 7. Better connection test

`testCloudCredentials()` splits into two reported conditions:

- **A. Reachable + authenticated** — `GET {url}/auth/v1/health` with the key, plus a cheap PostgREST root call. Key rejected vs. host unreachable are distinguished.
- **B. Schema provisioned** — the existing `stores` probe, now reported as a *warning* ("connected, POS schema not provisioned yet") instead of a failure. An empty table is a pass.

Saving is allowed on A-pass/B-warn. No RLS or policy changes.

## 8. Verification

- Typecheck + full vitest run, plus new tests: server-origin has no build fallback on terminals; `saveConnectionProfile` writes nothing on a failed test; readiness requires all three values; managed-integration import guard; test-result mapping for A/B states.
- Headless web load: sign-in screen renders and resolves the deployment's project.
- `MOBILE_BUILD=1` and `DESKTOP_BUILD=1` bundle builds followed by the existing artifact scan for project host, key prefixes, `VITE_SUPABASE`, `VITE_POS_SUPABASE`, `VITE_POS_SERVER_URL` and service-key shapes. Gradle APK and electron-builder packaging still run in CI; the same scan is wired there.
- Device scenarios B–L are exercised through unit/integration tests against the storage adapters (no real Android/Windows hardware in this sandbox); this limitation will be stated in the closing report.
- Version bump via `node scripts/bump-version.cjs`.
